# Ground-up review: on-target compiler + bcrun — performance, memory, C89 completion

2026-08-06. Read-only review before further scope expansion. No code was
changed. Four independent passes: current-state/doc reconciliation, memory
footprint, performance attribution, bit-field scoping. Numbers verified
against the built binaries and the git log through `818c1e289`; benchmark
figures are the freshest board-measured ones (commit messages, not the
manuals, hold the current numbers).

## 1. What is actually there today (supersedes several docs)

Pipeline: `cpp → cc0 → cc1 → cc2 → prog.bc → bcrun`.

* cc2 emits a version-3 (`BC_VERSION_NATIVE3`) mixed object. backend-bcode.c
  emits bytecode for every function; backend-thumb.c translates each
  function's bytecode span to Thumb-2 at `gen_epilogue`. A translated
  function gets a `BC_NATIVE` marker; on the board the dead bytecode is
  reclaimed by default (`THUMB_RECLAIM`, commit `c1f2ef3c5`).
* bcrun at load: streams fixups (never resident), binds library symbols once
  per symbol, takes the 512K VM heap from PSRAM once, and relocates the
  program to absolute machine addresses (`NOTES-absolute-addressing.md`,
  2026-08-03). A program address IS a machine address; r6 (old mem base) is
  permanently 0 — a spare register.
* Execution: main is entered native (v3). Native↔bytecode functions
  interoperate across a shared VM-stack frame layout. Doubles BL directly
  through helper-vector slots into the SDK's DCP routines; 19 libm doubles
  are called directly in kernel flash via the versioned table +
  `PICOIOC_LIBM` (commit `560b16f0b`, 2026-08-05).
* The "native cliff" is purely a size/limits policy now, NOT opcode
  coverage: translation bails on span > TMAX (48K board), native size >
  `THUMB_MAXFN` (40,000 bytes), LOCAL/ENTER offsets > 4095, pool overflow.
  Opcode coverage is complete — the `"opcode"` bail is effectively dead.

Current trustworthy numbers (RP2350B @ 378 MHz):

| build | Dhrystones/s |
|---|---|
| pure interpreter (2026-07-30 baseline) | 3,808 |
| current mixed native (2026-08-05, `560b16f0b`) | **103,548** |
| gcc -Os cross, same chip, Fuzix app | 367,864 |
| gcc -O2 cross | **379,022** |

Gap: 3.66×. Eclipse lineage ends at **2.26 s** (flash libm, 2026-08-05) vs
MMBasic 12.5 s.

## 2. Performance: where the 3.66× lives, and what to do about it

Method: host chain rebuilt, Dhrystone compiled through it, profiled under
qemu-arm with BCRUN_PROF/BCRUN_SITES, emitted Thumb disassembled, compared
against arm-none-eabi-gcc -O2.

Key facts:

* **All 13 Dhrystone functions translate native; 14 call sites become direct
  BL. Bytecode fallback contributes 0% of the gap.**
* Per iteration the runtime is crossed exactly 3 times: strcpy, strcmp
  (helper_call trampolines) and one BC_COPY (struct assign). Everything else
  is inline native code.
* The dominant cost is the stack-machine code shape: no register allocation
  (deliberate — PLAN-arm-backend.md:589), every local/arg read is 3
  instructions through the VM stack, every store 5, every constant operand
  ~5 with push/park bookkeeping. Proc_7 is 34 instructions where gcc -O2
  emits 4. gcc additionally inlines the struct assign as ldmia/stmia pairs
  and tail-calls.

Attribution of the ~2,800 excess cycles/iteration:

| category | share |
|---|---|
| stack-machine shape (locals in memory, addressing, r4 bookkeeping, constants) | ~65% |
| call machinery (args through VM stack, parity slot, ENTER/ARGS) | ~17% |
| library crossings (strcpy/strcmp trampolines, byte-wise lib_strcmp, BC_COPY marshal) | ~18% |
| bytecode fallback / helper dispatch / FP / symbol binding | 0% (all already fixed or absent) |

Ranked opportunities (payoff-per-effort):

1. **Direct `[r4,#off]` addressing for locals/args** — fold `LOCALn;LOADx`
   into one `ldr r0,[r4,#n]`, and use the existing `t_track.slot` machinery
   to turn push-addr…STOREx into `str r0,[r4,#n]`. r6==0 makes every
   load/store single-instruction-capable already. Est. 20-30% off Dhrystone
   cycles (~125-140k/s). Moderate effort, low-moderate risk, same class as
   the shipped seam/fusion passes, gated by the existing 5-way harness.
2. **Constants folded into operands** — `PUSH;CONSTk;ADD/CMP` →
   `adds r0,#k` / `cmp r0,#k`. The parked stage-8 gen_direct candidate.
   Est. 10-20% on top of #1 (composes on loop-bound compares).
   Small-moderate effort, low risk.
3. **Fast-slot string/memory libcalls** — give strcpy/strcmp/memcpy/strlen
   direct helper-vector slots like the DCP ops; make lib_strcmp word-wise.
   Est. 5-10% Dhrystone; benefits all string-heavy code incl. mmb2c output.
   Small effort (mirror of the shipped DCP-slot work).
4. **Inline small constant-length BC_COPY** as ldmia/stmia (length known at
   translate time). ~4%. Small effort.
5. **Elide r4 adjust pairs inside verified fused windows.** 3-5%. Small
   effort, moderate risk (the stage-10 hazard class).
6. Register caching of hot locals (regalloc-lite, r7-r11): the only route
   past ~2× off gcc. Large effort, high risk — the point where a
   bytecode-span translator starts fighting its own source of truth.
   Explicitly declined in the plan, correctly at the time.
7. cc1 inlining/CSE: park; routes upstream to the Compiler Kit.

**Ceiling:** items 1-5 plausibly land ~170-220k D/s (45-58% of gcc -O2);
pure loops move from 2-3× off gcc to ~1.3-1.8×. Reaching gcc -O2 itself is
not realistic in this design — the last 2× is exactly what the frame-parity
mixed-mode architecture traded away (args/locals in registers, inlining,
loop transforms); that is a rewrite, not an increment. Calibration: gcc -O0
produces this design's shape and runs 2-2.5× slower than -O2, so ~40-55% of
-O2 is the natural resting point of a well-peepholed stack-frame machine.
The current ~27% says there is real headroom; ~200k/s is attainable,
~380k/s is a different project.

## 3. Memory: the per-process bill and what's reducible

No MMU; every binary is a private copy (swapper moves 4K chunks). Every
running .bc program is one full bcrun process via the `#!` line.

Floor, before the program loads (arm-none-eabi-size on the current board
build):

| item | bytes |
|---|---|
| bcrun text+rodata (incl. 26.9K mm BASIC runtime, ~14K interpreter core, 5.2K relinked libm, ~2K single-float softfloat, ~17K libc) | 67,796 |
| ELF .dynamic/.dynsym/.rel.dyn/.hash/.dynstr LOAD segment, resident after relocation | 13,697 |
| data + bss (incl. 2K getstr buffers, 4K graphics batch, 2K always-on profiling arrays, stdio, misc) | 13,460 |
| udata | 1,536 |
| native C stack (USERSTACK) | 8,192 |
| **floor** | **~104.5K** (~31% of the 340K pool) |

Per program on top: code[] (Dhrystone 9.7K, eclipse 100.5K), data+bss,
sym+strtab+bind kept for the whole run (eclipse 16.3K), mem[] demand-sized
(NULLGUARD + data/bss + 4,240 mm pools + 8K STACKROOM + 2K slack). Trivial
utility ≈ 135K total; the eclipse ≈ 250K of 340K. Already moved out and NOT
a problem: VM heap (512K in PSRAM), fixups (streamed), dead bytecode
(reclaimed), the old static 48K mem[].

Reduction options, by value-per-risk:

* **R1. Free the ELF dynamic/reloc segment after relocation — ~13.7K, low
  risk.** It sits above bss and is only read during plt_relocate_rel; set
  u_break back to end-of-bss (syscall_execelf32.c) and the heap reclaims it.
  Benefits every ELF process on the port, not just bcrun.
* **R2. Route mmb_runtime's direct pow/atan2/log10/sqrt calls through the
  kernel libm table — ~5.2K, low risk.** The shared-table mechanism only
  covers calls through mfns[]; mm_* code calls these directly so the linker
  re-links private copies of functions the kernel already exports. Macro
  shims ahead of the include, exactly like the existing strtoll macros.
  The DCP-backed shared copy measured faster, not slower.
* **R3. Lazy profiling arrays — 2K, trivial.** prof_op/prof_lib are resident
  even with BCRUN_PROF unset; prof_site is already lazy.
* **R4. Eager libcall binding, then free sym+strtab — ~12K on big programs,
  medium effort.** Bonus: "no runtime function X" becomes a load-time
  refusal instead of a mid-run exit(1).
* **R5. Resident bcrun (text in flash, per-process data only) — up to ~68K
  per process, high effort, medium-high risk.** All precedents exist
  in-tree (kernel-in-flash with per-function RAM excludes, libm export).
  Would cut the floor to ~37K and make concurrent .bc programs cheap. But
  bc_exec is a tight loop and flash-XIP tight loops measured 2.7× slower,
  so the hot core needs copy-to-RAM excludes; adds kernel↔runtime
  versioning. **Only worth it if the roadmap needs >2 concurrent .bc
  processes.** Not now.
* R6. Split bcrun/bcrun-basic (~33K for plain-C processes): weak version of
  R5 with most of its drift risk. Only if R5 is rejected AND multi-process C
  workloads matter.
* R7. `BCRUN_CODE=psram` opt-in for jumbo programs (>200K objects run at
  all, at known XIP cost). Small effort, never a default.

Leave alone (reviewed, not worth it): STACKROOM/USERSTACK sizes (silent
overflow risk in a no-guard flat space), MM_BATCH 512, getstr 4×512
rotation (printf contract), unconditional mm pools (the sizing-rule comment
is right), MEMSIZE cap (BCRUN_MEM exists), bind-table layout, udata + 4K
chunk rounding (architecture). The port has already harvested the easy
memory; below the R5 cliff, R1+R2+R3 (~21K, all low risk) + R4 (~12K) is
what's left.

## 4. Bit fields: the design exists, the payoff mostly doesn't

**STATE.md's stated blocker is no longer true.** "The tree has no temporary
to hold the container address in" — the struct-return work (same day as
that note) added exactly that mechanism: assign_storage(S_AUTO) + a fresh
T_LOCAL (expression.c:222-236). And compound assignment already does
single-evaluation RMW through a computed address today (the address subtree
appears once; exec_eqop pops it once; the Thumb translator inlines the same
contract). STATE.md should be corrected regardless of when the work is done.

Recommended design (scoped in detail; ~5-7 working days to hardware-verified):

* cc1-only. Parse `: const-expr` in struct_declaration(); grow the member
  tuple 3→4 words (bitinfo word; exactly four reader sites); LSB-first
  layout within a sizeof(declared-type) unit, no straddling — identical on
  the x86-64 host and AAPCS32, so gcc stays the differential oracle.
* New cc1-internal T_BITFIELD lvalue node that never reaches cc2: reads
  lower in make_rval to shift/mask (arithmetic-shift pair for signed);
  writes lower through a hidden address temporary + T_COMMA (the
  struct-return pattern), skipping the temp when the address subtree is
  provably pure. Assignment value = stored value re-extracted.
* **Zero changes to bytecode.h, backend-bcode, backend-thumb, bcrun, bcdump
  — no board resend of anything but cc1.** The lowered ops are already in
  the translator's covered set. Every other Compiler Kit backend gains
  bitfields free, which makes it a clean upstream PR (diff against the live
  kit's struct.c first — the vendored copy is stale).
* Static initializers need real work (packing consecutive bitfield
  constants into one container in ini_struct) — the item everyone forgets.
* Risk register headline: `&s.f` must become a diagnostic (expression.c's
  generic LVAL strip would otherwise silently yield a container pointer);
  gate any pure-address fast path on !(SIDEEFFECT|IMPURE); use cval_t for
  masks (host-64-bit trap).

**Recommendation: keep the loud refusal for now.** Implementing it gains
zero conformance tests (the suite's only bitfield test, 00218, uses an
enum-typed field that is itself not C89 — gcc -std=c89 -pedantic-errors
refuses the whole file; 165/175 does not move). A tree-wide sweep found
bitfield declarations in exactly two files reachable by this ecosystem
(platform-esp8266 devsdspi.c and Library/libs/resolv.h) — PLAN-c89-gaps'
list of expected users (console.c, fat.c, stty.c) does not check out in
this tree. The "compile real Fuzix sources" trigger stands, and it is
weaker than the plan thought. When it fires, the design above is the shape:
front-end-only, upstreamable, one uusend of a stripped cc1.

## 5. Overall verdict and suggested order

The current solution is **good**: the architecture (bytecode as single
source of truth, per-function native translation, frame-parity mixed mode,
DCP doubles, shared flash libm, PSRAM heap) is coherent, board-proven, and
has already harvested the large wins on both axes. Nothing found is wrong;
what remains is a short list of increments with known shapes:

1. Perf #1 (direct [r4,#off] addressing) then #2 (constant operands) —
   together plausibly ~1.5-2× on Dhrystone-like code; the gates already
   exist (5-way qemu differential + board).
2. Mem R1 (free ELF reloc segment — helps every process on the port),
   R2 (libm shims), R3 (lazy prof arrays): ~21K/process, all low risk.
3. Opportunistic: perf #3/#4 (string fast slots, inline small COPY),
   mem R4 (eager bind) — small, independent.
4. Defer: resident bcrun (R5) until >2 concurrent .bc processes is a real
   requirement; regalloc-lite (perf #6) until 200k/s is demonstrably not
   enough; bitfields until self-hosting demands them.
5. Doc hygiene now: correct STATE.md's bitfield-blocker paragraph, mark
   BYTECODE.md as v1-frozen with a pointer to bytecode.h, append the
   post-07-31 stages to PLAN-arm-backend.md's status section.

Per the house rule: every estimate above that matters (perf #1/#2 payoff,
R1/R2 savings) is host/qemu-derived or source-derived and needs board
verification before being believed.
